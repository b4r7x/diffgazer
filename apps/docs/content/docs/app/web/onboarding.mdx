title: Onboarding
description: First-run setup, step by step, before your first review.
---

The first time you open Diffgazer in web mode it has no configuration to work with, so it shows a setup wizard instead of the Home screen. You only see this once: it walks you through the setup plan for the product you pick and saves a working configuration at the end. After that, Diffgazer returns to Home, where you choose **Review Unstaged** or **Review Staged** to start your first review. You can change any setup choice later from [Settings](/app/web/settings). This page covers each step in order. For the bigger picture of what web mode looks like once setup is done, see the [web overview](/app/web).

The wizard does not run a fixed list of screens. It runs the **setup plan of the product you selected**: Product, then Endpoint, Authentication, Model, Conformance, and Notice. A product that binds no endpoint — the local CLI products — has no Endpoint step, so its plan is five steps instead of six. A stepper across the top shows the plan, and a line under it reads out where you are, for example `Step 2 of 6: Endpoint`. Use Next to move forward and Back to revisit a step; the Next button stays disabled until the current step is satisfied.

## Select a product

The first step lists the thirteen selectable products, each with its description and a billing-tier badge derived from how the product bills you. Hosted APIs read FREE when every model the catalog lets them offer is zero-priced, FREE/PAID when they sell both, FREE TIER when every offerable model carries a list price but the product publishes a no-cost quota to run it on, and PAID otherwise. LOCAL marks products you run yourself over loopback HTTP, and AMBIENT marks vendor CLIs that ride a subscription you already pay for. FREE is only ever a claim about a published price; FREE TIER is a claim about an account's quota, so it comes with the limits the product's own notice describes. Diffgazer does not ship a model of its own, so you bring a product you already have access to: a hosted API, a local HTTP server on loopback, or a vendor CLI you already signed in to. Selecting a product builds the rest of the plan around it and resets any draft you had started for a different product. For the full list and what each one implies, see [providers and models](/app/concepts/providers-and-models) and the [providers reference](/app/reference/providers).

## Configure the endpoint

Hosted products ask you to choose the endpoint tuple: a list of allowed endpoint profiles, each showing its label and the exact URL it binds. When a profile is region-bound the region comes with it, and when it is workspace-bound the step also asks for a workspace reference.

Local HTTP products ask for the loopback preset instead — `http://127.0.0.1:11434` for Ollama, and either LM Studio (`http://127.0.0.1:1234/v1`) or llama.cpp (`http://127.0.0.1:8080/v1`) for the Local OpenAI-compatible product. Diffgazer verifies that the first network hop is loopback; anything downstream of your local server is the server operator's responsibility.

Local CLI products bind no endpoint, so the plan skips this step entirely.

## Configure authentication

What this step asks for depends on the transport:

- **Hosted API.** Pick how the credential is supplied. **Enter credential now** takes the key in a masked, write-only field. **Use environment reference** binds the product's environment variable instead, so nothing secret is stored — the server resolves the value at run time. See [Environment variables](/app/reference/environment-variables) for the name each product reads.
- **Local HTTP.** No hosted credential is stored. If your server expects one, tick **This server requires a bearer token** and supply the token in the write-only field.
- **Local CLI.** Diffgazer uses vendor-managed local auth: install and sign in with the vendor's own CLI, then identify that installation here. Diffgazer never asks for CLI tokens or auth file paths and does not import or proxy them.

## Select a model

For hosted products, the wizard discovers models for the configuration tuple you just built and the selection is exact — aliases are rejected. To discover models against a real record, the wizard first persists the draft configuration server-side, then reads the model list back through `GET /api/config/providers/:configurationId/models`. That draft is revoked again when you change the tuple or leave the wizard, so an abandoned setup does not leave a configuration behind.

Local HTTP and local CLI products are different: the **Model** step shows **Catalog observations are unavailable for this configuration product.** with **Retry** only. There is no model list, **Next** stays disabled, and an external `select` through the [local API](/app/reference/api) does not update the wizard draft. You cannot complete setup for these products inside the wizard today. Finish model selection, conformance, and notice acceptance through the [local-product API sequences](/app/reference/configuration) or **Configure Provider** in Settings instead. See [providers and models](/app/concepts/providers-and-models#local-http-and-local-cli-products).

If discovery fails or returns nothing for a hosted product, the step says so and offers **Retry**. Products whose model policy already pins the acceptable IDs show that list directly instead.

## Verify conformance

The conformance step is where you confirm that the configured tuple and the exact model you picked are ready to be verified against the product's required checks, and where the cost of the optional **Test readiness** probe is disclosed. Saving does not run that probe: your first review verifies structured review support and records the result. Tick the confirmation to continue.

Changing anything upstream invalidates this: editing the configuration or picking a different model resets conformance to not-tested and takes the notice acceptance back to required, so you re-confirm what actually changed.

## Accept the product notice

The last step shows the current product's billing and privacy notice — the real lines for that product, not a generic blurb — and requires explicit acceptance. Notices are versioned; acceptance is recorded against the exact notice ID and version, and a material change to the notice asks again.

On this final step the button reads Complete Setup. Activating it saves the configuration and returns you to Home. Choose **Review Unstaged** or **Review Staged** there to start your first review. From here on, Diffgazer skips the wizard.

> Tip: every step is keyboard-driven. Use the arrow keys to move through options, Space to select the highlighted one, and Enter to select and advance in a single keystroke. `↓` from the last option moves into the Back / Complete Setup buttons.
